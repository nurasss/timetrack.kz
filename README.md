# timetrack.kz

Мульти-тенантный учёт рабочего времени по распознаванию лица. PWA на чистом JS + лёгкий бэкенд (PHP в проде или Node.js), без базы данных — данные хранятся в JSON-файлах на диске.

> Этот файл — единая точка входа в документацию проекта. Для анализа того, что не хватает до запуска в production, см. `production-readiness.md` в памяти проекта (auto-memory Claude).

## Архитектура

```
                     ┌────────────────────┐
  Браузер посетителя │   index.html        │  лендинг + регистрация компании
                     └─────────┬──────────┘
                               │ action=register / companies
                               ▼
                     ┌────────────────────┐
  Браузер админа     │   admin.html?c=slug │  сотрудники / дашборд / табель / XLSX
                     └─────────┬──────────┘
                               │ action=state / saveEmployee / ...  (+ adminPin)
                               ▼
                     ┌────────────────────┐
  Планшет-киоск       │   tablet.html?c=slug│  распознавание лица в браузере (face-api.js)
                     └─────────┬──────────┘
                               │ action=state / addLog
                               ▼
                     ┌────────────────────┐
                     │      api.php        │  прод. API (PHP)  ИЛИ  server.js/server.vps.js (Node)
                     └─────────┬──────────┘
                               ▼
                     data/{slug}/store.json   ← по одному JSON-файлу на компанию
                     data/companies.json      ← публичный реестр slug + название
```

**Мульти-тенантность.** Каждая компания получает свой `slug` (например `poscenter`), который передаётся во всех запросах как `?c=slug`. Данные физически изолированы: `data/{slug}/store.json`. Общий реестр компаний — `data/companies.json` (slug + название, без PIN и без сотрудников).

**Распознавание лица — полностью на клиенте.** Сервер никогда не запускает ML-модели: `tablet.html` загружает face-api.js и веса моделей (`models/`) прямо в браузере, сравнивает дескриптор лица перед камерой с дескрипторами сотрудников компании (которые он получил через `action=state`) и сам решает, кто пришёл. Это значит, что сервер не нагружен распознаванием, но и не может проверить, что сравнение действительно произошло на стороне клиента — это архитектурное решение, а не баг.

## Модель данных

Файл `data/{slug}/store.json`:

```jsonc
{
  "employees": [
    {
      "id": "e1234567890123",
      "fname": "Иван",
      "lname": "Петров",
      "position": "Сотрудник",
      "dept": "Общий",
      "workStart": "09:00",          // HH:MM, время начала смены — для расчёта опозданий
      "photo": "data:image/jpeg;...", // base64, ≤ 1.6 МБ, может быть null
      "descriptor": [0.123, ...]      // 64–256 чисел, дескриптор лица face-api.js
    }
  ],
  "logs": [
    {
      "id": "l1718000000000",
      "empId": "e1234567890123",
      "empName": "Иван Петров",
      "empPhoto": null,
      "type": "checkin",            // checkin | checkout
      "time": "09:03",
      "date": "25.06.2026",
      "ts": "2026-06-25T03:03:00.000Z", // ISO, источник истины для дублей/сортировки
      "isLate": false,
      "verification": "blink"       // blink | head | ""
    }
  ],
  "settings": {
    "recognitionModel": "tiny",     // tiny | ssd — какую модель face-api.js грузить
    "matchThreshold": 0.55,         // евклидов порог совпадения дескрипторов (0.35–0.8)
    "lateMinutes": 15,              // допуск опоздания в минутах
    "adminPin": "1234"              // PIN админки, НИКОГДА не отдаётся клиенту (см. public_state)
  }
}
```

Реестр `data/companies.json`:

```jsonc
[
  { "slug": "poscenter", "name": "ПосЦентр", "createdAt": "2026-06-20T05:50:43.784Z" }
]
```

**Лимиты, зашитые на бэкенде:** фото ≤ 1.6 МБ base64; `logs` хранит не более 10 000 последних записей (старые молча отрезаются); дубль-защита — одна и та же отметка (`empId` + `type`) в окне 120 секунд отклоняется с `409`.

## API

Все запросы — `GET`/`POST` на `api.php` (или `server.js`/`server.vps.js` с тем же контрактом). Action передаётся как `?action=...` (или в теле JSON), компания — как `?c=slug`. Ответ всегда `{ ok: true, ... }` либо `{ ok: false, error: "..." }` с соответствующим HTTP-статусом.

| Action | Метод | Требует `c` | Требует `adminPin` | Описание |
|---|---|---|---|---|
| `register` | POST | — | — | Регистрация новой компании: `{ slug, name, pin }`. |
| `companies` | GET | — | — | **Публичный** список всех компаний (slug + название). Используется лендингом. |
| `companyInfo` | GET | ✓ | — | Название компании по slug (для брендинга в шапке admin/tablet). |
| `state` | GET | ✓ | — | Полное состояние компании (сотрудники + логи + настройки **без** `adminPin`). |
| `checkAdminPin` | POST | ✓ | ✓ | Проверка PIN при входе в админку. Возвращает `state` при успехе. |
| `saveEmployee` | POST | ✓ | ✓ | Создать/обновить сотрудника (`employee.id` пустой → новый). |
| `deleteEmployee` | POST | ✓ | ✓ | Удалить сотрудника по `id`. |
| `addLog` | POST | ✓ | — | Добавить отметку прихода/ухода. `409`, если дубль за последние 120 сек. |
| `updateSettings` | POST | ✓ | ✓ | Обновить `settings` (PIN, модель, порог, допуск опозданий). |
| `clearLogs` | POST | ✓ | ✓ | Очистить все логи компании. |
| `deleteCompany` | POST | ✓ | ✓ + ввод slug | Полное удаление компании и всех её данных. Доступно в `api.php`/`server.js`, **отсутствует** в `server.vps.js`. |

Примечания:
- `addLog` не требует `adminPin` намеренно — отметки делает планшет, у которого нет (и не должно быть) PIN админки.
- `state`/`companies` не требуют авторизации вообще — см. [Безопасность](#безопасность), это сознательно принятый риск на текущем этапе.
- CORS открыт всем (`Access-Control-Allow-Origin: *`) на всех трёх бэкендах.

## Распознавание лица и liveness

Всё происходит в браузере планшета (`tablet.html`), сервер не участвует:

1. При регистрации сотрудника в админке (`admin.html`) камера снимает кадр, face-api.js считает 128-мерный дескриптор лица и сохраняет его вместе с фото в `employee.descriptor`/`employee.photo`.
2. На планшете каждые ~2.2 сек (`FULL_MATCH_INTERVAL_MS`) face-api.js детектирует лицо в кадре и считает евклидово расстояние (`faceapi.euclideanDistance`) между текущим дескриптором и дескрипторами всех сотрудников компании.
3. Совпадение засчитывается, если расстояние ≤ `settings.matchThreshold` (по умолчанию 0.55, настраивается 0.35–0.8 в админке).
4. Модель детекции выбирается в настройках: `tiny` (TinyFaceDetector, быстрее) или `ssd` (SSD MobileNetV1, точнее, тяжелее).
5. **Liveness-проверка** (анти-спуфинг): сотрудник должен моргнуть либо повернуть голову — это подтверждает, что перед камерой живой человек, а не фото на экране другого телефона. Реализовано через анализ EAR (eye-aspect-ratio) по `face_landmark_68` лендмаркам, с историей экспериментов и провалов в `data/git log` (опробованы и отброшены: пассивная проверка по фото, оптическая флеш-проверка, MiniFASNet-V2 — все не сработали на реальном железе или были обойдены).

**Текущий уровень защиты — одно подтверждённое моргание/поворот головы.** Известный риск: можно показать камере видео (а не статичное фото) с лицом коллеги и пройти проверку — buddy punching. Подробности и история попыток — в памяти `anti-spoofing-findings`.

## Фронтенды

### `index.html` — лендинг
- Грузит и показывает публичный список компаний (`action=companies`).
- Форма регистрации: slug (латиница/цифры/дефис, 3–32 символа), название, PIN (≥4 символа) → `action=register` → редирект на `admin.html?c=slug`.

### `admin.html` — админка
- Вход по PIN (`checkAdminPin`), PIN кешируется в `sessionStorage` на время сессии браузера.
- **Дашборд** — кто сейчас на месте/опоздал, по сегодняшним логам.
- **Сотрудники** — CRUD, захват фото и дескриптора лица через камеру или загрузку файла.
- **Отчёты/табель** — фильтры по периоду/сотруднику, агрегация рабочих часов, экспорт в XLSX (через встроенный генератор) и CSV — и для табеля, и для сырых отметок.
- **Настройки** — смена PIN, порог распознавания, модель детекции, допуск опозданий (минуты), удаление компании (требует PIN + ручной ввод slug подтверждения).
- Кеширует state в `localStorage` (`STORE_KEY = timetrack_state_{slug}`) для быстрого повторного открытия.

### `tablet.html` — киоск
- Полноэкранный PWA-режим, ландшафтная ориентация, Wake Lock (не даёт экрану засыпать).
- Камера + распознавание + liveness (см. выше), кнопки «Пришёл» / «Ушёл» с защитой от повторной отметки (дубли отклоняются и на клиенте, и на сервере).
- Детект бездействия: после `SLEEP_AFTER_MS` (45 сек) уходит в режим ожидания, экономит ресурсы.
- Индикатор синхронизации (`Сервер` / `Локально · N в очереди`) — см. [Офлайн-режим](#офлайн-режим).
- Каждые 20 сек подтягивает свежий `state` с сервера (на случай если сотрудника добавили/удалили из админки).

## PWA / Service Worker

`sw.js` кеширует статические страницы (`index.html`, `admin.html`, `tablet.html`), манифест, иконки и **все веса моделей face-api.js**, чтобы планшет мог запуститься и узнавать лица даже при недоступном интернете. API (`/api.php`) и не-GET запросы из кеша исключены намеренно — кешировать данные нельзя, только статику и модели. При обновлении версии нужно поднять `CACHE_NAME` (`timetrack-pwa-v20` → `v21`...), иначе старые клиенты не увидят новых файлов.

## Офлайн-режим

Реализовано 2026-06-25. Раньше отметки, сделанные при недоступном интернете, не сохранялись (полная потеря данных учёта времени при сбое связи).

Текущая схема в `tablet.html`:
1. `Store.post('addLog', ...)` пытается отправить отметку на сервер.
2. Если сеть недоступна — отметка **(а)** сразу применяется локально (`state.logs.unshift`, мгновенный фидбек сотруднику) и **(б)** кладётся в персистентную очередь `localStorage['timetrack_queue_{slug}']` (`enqueueLog`).
3. Очередь дренируется (`flushQueue`) при: успешном `Store.load()`, успешном следующем `Store.post()`, и событии браузера `online`.
4. Отправка идёт по порядку (oldest-first), с защитой от дублей по `id`. Сервер отвечает `409`, если у него уже есть эквивалентная отметка (окно 120 сек) — такая запись тоже считается доставленной и удаляется из очереди. Любая другая ошибка сервера останавливает дренаж (без бесконечного спина на «ядовитой» записи) — попытка будет повторена при следующем триггере.
5. Индикатор синхронизации показывает количество отметок, ожидающих отправки: `Локально · N в очереди`.

## Безопасность

Авторизация — единый PIN на компанию (`settings.adminPin`), хранится **в открытом виде** в `store.json`, передаётся в каждом запросе. Защита от подбора PIN на бэкенде отсутствует.

**Сознательно принятые риски (закреплены решением 2026-06-25):**
- `action=state` отдаёт фото и биометрические дескрипторы сотрудников **без проверки PIN** — это нужно планшету для распознавания лиц, у которого нет своих учётных данных.
- `action=companies` публично перечисляет все зарегистрированные компании — используется лендингом для каталога.
- Совокупный эффект: зная (или подобрав) slug компании, можно прочитать список сотрудников вместе с их фото и дескрипторами лиц без какой-либо авторизации.

Подробный список того, чего не хватает для безопасного запуска в production (включая эти риски, защиту от перебора PIN, бэкапы, биллинг, требования закона РК «О персональных данных»), а также то, что уже исправлено — см. `production-readiness.md` в auto-memory проекта.

Что уже сделано:
- `adminPin` исключается из всех публичных ответов (`public_state`/`publicState`).
- Каталог компании под `.htaccess` `Require all denied` (PHP-прод).
- Удаление компании требует PIN **и** ручного ввода slug для подтверждения.
- Серверный лок на запись (`flock`/файловый лок) — конкурентные запросы к одной компании не бьют друг друга по данным.

## Локальная разработка

```bash
node "timetrack poscenter/server.js"
# открыть http://localhost:8787/
# планшет:  http://localhost:8787/tablet.html?c=poscenter
# админка:  http://localhost:8787/admin.html?c=poscenter
```

`server.js` отдаёт и статику, и API на одном порту (`PORT`, по умолчанию `8787`). Тестовые компании (`poscenter`, `other-co`) уже есть в `data/`.

## Деплой

Продакшн (см. память `server-structure`):
- **Веб-сервер:** Caddy.
- **Статика:** отдаётся файл-сервером напрямую.
- **API (`/api.php*`):** обрабатывается напрямую PHP (если хостинг с PHP) **или** проксируется на Node.js-контейнер с `server.vps.js`.
- Деплой — вручную (rsync на сервер), без CI/CD. Подробный процесс и серверные особенности — в памяти `server-structure`/`deployment-state`.

## Известные ограничения

- **`server.vps.js` отстаёт от `api.php`/`server.js`**: на момент написания не реализует `deleteCompany`. Логика одного и того же API дублируется вручную в трёх местах (`api.php`, `server.js`, `server.vps.js`) — при любом изменении контракта нужно править все три или явно выбрать один источник правды.
- **Нет базы данных** — JSON-файл на компанию, полная перезапись на каждое изменение. Подходит для раннего этапа, не масштабируется на десятки активных компаний одновременно.
- **Нет биллинга, email-верификации, восстановления PIN** — регистрация мгновенная и бесплатная, без подтверждения контакта.
- **`timetrack-legacy.html`** оставлен в репозитории для истории, в проде не используется и не поддерживается.

Полный и приоритизированный список (с критичностью и статусом фикса) — в auto-memory: `production-readiness.md`.
