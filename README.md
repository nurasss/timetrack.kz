# timetrack.kz

Мульти-тенантный учёт рабочего времени по распознаванию лица. PWA на чистом JS + лёгкий бэкенд (PHP в проде или Node.js), без базы данных — данные хранятся в JSON-файлах на диске.

> Этот файл — единая точка входа в документацию проекта. Для анализа того, что не хватает до запуска в production, см. `production-readiness.md` в памяти проекта (auto-memory Claude).

## Архитектура

```
  Браузер посетителя ──▶ index.html (лендинг, без форм)
                            │              │
                  "Подключить компанию"   "Войти"
                            ▼              ▼
                      register.html   login.html
                      action=register   действует по slug ИЛИ названию:
                      → письмо с          1) action=companies — резолв в slug
                        подтверждением    2) action=checkAdminPin — проверка PIN
                      action=confirmEmail │
                            │              │ при успехе — sessionStorage + редирект
                            ▼              ▼
                     ┌────────────────────┐
  Браузер админа     │   admin.html?c=slug │  сотрудники / дашборд / табель / XLSX
                     └─────────┬──────────┘
                               │ action=state / saveEmployee / ...  (+ adminPin)
                               ▼
                     ┌────────────────────┐
  Планшет-киоск       │   tablet.html?c=slug│  распознавание лица в браузере (face-api.js)
                     └─────────┬──────────┘
                               │ action=state / addLog
                               ▼
                     ┌────────────────────┐
                     │      api.php        │  прод. API (PHP)  ИЛИ  server.js/server.vps.js (Node)
                     └─────────┬──────────┘
                               ▼
                     data/{slug}/{employees,settings,logs}.json  ← по три JSON-файла на компанию
                     data/companies.json                          ← публичный реестр slug + название
```

**Мульти-тенантность.** Каждая компания получает свой `slug` (например `poscenter`), который передаётся во всех запросах как `?c=slug`. Данные физически изолированы в `data/{slug}/`. Общий реестр компаний — `data/companies.json` (slug + название + email + флаг подтверждения, без PIN и без сотрудников).

**Распознавание лица — полностью на клиенте.** Сервер никогда не запускает ML-модели: `tablet.html` загружает face-api.js и веса моделей (`models/`) прямо в браузере, сравнивает дескриптор лица перед камерой с дескрипторами сотрудников компании (которые он получил через `action=state`) и сам решает, кто пришёл. Это значит, что сервер не нагружен распознаванием, но и не может проверить, что сравнение действительно произошло на стороне клиента — это архитектурное решение, а не баг.

## Модель данных

Данные каждой компании разнесены на **три файла** в `data/{slug}/` (с 2026-06-25 — раньше был один общий `store.json`, см. [Известные ограничения](#известные-ограничения)):

`data/{slug}/employees.json` — меняется только при `saveEmployee`/`deleteEmployee`:

```jsonc
{
  "employees": [
    {
      "id": "e1234567890123",
      "fname": "Иван",
      "lname": "Петров",
      "position": "Сотрудник",
      "dept": "Общий",
      "workStart": "09:00",          // HH:MM, время начала смены — для расчёта опозданий
      "photo": "data:image/jpeg;...", // base64, ≤ 1.6 МБ, может быть null
      "descriptor": [0.123, ...]      // 64–256 чисел, дескриптор лица face-api.js
    }
  ]
}
```

`data/{slug}/settings.json` — меняется только при `updateSettings`:

```jsonc
{
  "settings": {
    "recognitionModel": "tiny",     // tiny | ssd — какую модель face-api.js грузить
    "matchThreshold": 0.55,         // евклидов порог совпадения дескрипторов (0.35–0.8)
    "lateMinutes": 15,              // допуск опоздания в минутах
    "adminPin": "1234"              // PIN админки, НИКОГДА не отдаётся клиенту (см. public_state)
  }
}
```

`data/{slug}/logs.json` — меняется на каждый `addLog`/`clearLogs` (самый частый писатель, поэтому изолирован от тяжёлых фото/дескрипторов в employees.json):

```jsonc
{
  "logs": [
    {
      "id": "l1718000000000",
      "empId": "e1234567890123",
      "empName": "Иван Петров",
      "empPhoto": null,
      "type": "checkin",            // checkin | checkout
      "time": "09:03",
      "date": "25.06.2026",
      "ts": "2026-06-25T03:03:00.000Z", // ISO, источник истины для дублей/сортировки
      "isLate": false,
      "verification": "blink"       // blink | head | ""
    }
  ]
}
```

Дополнительно на каждую компанию: `data/{slug}/security.json` — счётчик неверных попыток PIN и `lockUntil` (см. [Безопасность](#безопасность)); `data/{slug}/backups/employees-{timestamp}.json` — последние 20 снапшотов `employees.json`, по одному на каждое сохранение сотрудника.

Реестр `data/companies.json`:

```jsonc
[
  {
    "slug": "poscenter",
    "name": "ПосЦентр",
    "createdAt": "2026-06-20T05:50:43.784Z",
    "consent": { "policy": true, "offer": true, "acceptedAt": "2026-06-20T05:50:43.784Z" }
  }
]
```

**Лимиты, зашитые на бэкенде:** фото ≤ 1.6 МБ base64; `logs` хранит не более 10 000 последних записей (старые молча отрезаются); дубль-защита — одна и та же отметка (`empId` + `type`) в окне 120 секунд отклоняется с `409`.

**Миграция со старого формата.** Если в `data/{slug}/` ещё лежит только legacy `store.json` (компания создана до 2026-06-25), при первом же запросе к ней бэкенд автоматически разносит данные на три новых файла и переименовывает `store.json` → `store.json.migrated` (не удаляется, оставлен как страховочная копия). Миграция идемпотентна и происходит один раз на компанию.

## API

Все запросы — `GET`/`POST` на `api.php` (или `server.js`/`server.vps.js` с тем же контрактом). Action передаётся как `?action=...` (или в теле JSON), компания — как `?c=slug`. Ответ всегда `{ ok: true, ... }` либо `{ ok: false, error: "..." }` с соответствующим HTTP-статусом.

| Action | Метод | Требует `c` | Требует `adminPin` | Описание |
|---|---|---|---|---|
| `register` | POST | — | — | Регистрация новой компании: `{ slug, name, pin, email, acceptedPolicy, acceptedOffer }`. Все поля обязательны (`422` если нет), включая корректный `email`. Компания создаётся **неактивной** (`emailVerified: false`) — шлёт письмо с ссылкой подтверждения, не welcome-письмо. |
| `confirmEmail` | POST | ✓ | — (вместо него `token`) | `{ token }`. Подтверждает email по ссылке из письма (24 часа), ставит `emailVerified: true`. После этого компания разблокируется. |
| `resendConfirmation` | POST | ✓ | — | `{ email }`. Если компания ещё не подтверждена и email совпадает — шлёт письмо повторно (кулдаун 2 мин). Ответ всегда `{ ok: true }`. |
| `companies` | GET | — | — | **Публичный** список всех компаний (slug + название). Используется `login.html` для резолва ввода (slug или название) в конкретный slug. Не зависит от `emailVerified`. |
| `companyInfo` | GET | ✓ | — | Название компании по slug (для брендинга в шапке admin/tablet). Доступно даже неподтверждённым компаниям. |
| `state` | GET | ✓ | — | Полное состояние компании (сотрудники + логи + настройки **без** `adminPin`). `403 EMAIL_NOT_VERIFIED`, если email не подтверждён. |
| `checkAdminPin` | POST | ✓ | ✓ | Проверка PIN при входе в админку. Возвращает `state` при успехе. `429` при блокировке, `403 EMAIL_NOT_VERIFIED` если email не подтверждён (см. [Безопасность](#безопасность)). |
| `requestPinReset` | POST | ✓ | — | `{ email }`. Если email совпадает с указанным при регистрации — шлёт письмо со ссылкой сброса (токен на 30 мин). Ответ всегда `{ ok: true }` независимо от совпадения (не палит, какой email привязан к компании). Кулдаун 2 мин между запросами. |
| `resetPin` | POST | ✓ | — (вместо него `resetToken`) | `{ resetToken, newPin }`. Проверяет токен (константное сравнение) и срок действия, ставит новый `adminPin`, инвалидирует токен. |
| `saveEmployee` | POST | ✓ | ✓ | Создать/обновить сотрудника (`employee.id` пустой → новый). После записи делает снапшот в `backups/`. |
| `deleteEmployee` | POST | ✓ | ✓ | Удалить сотрудника по `id`. |
| `addLog` | POST | ✓ | — | Добавить отметку прихода/ухода. `409`, если дубль за последние 120 сек. |
| `updateSettings` | POST | ✓ | ✓ | Обновить `settings` (PIN, модель, порог, допуск опозданий). |
| `clearLogs` | POST | ✓ | ✓ | Очистить все логи компании. |
| `deleteCompany` | POST | ✓ | ✓ + ввод slug | Полное удаление компании и всех её данных. Доступно в `api.php`/`server.js`, **отсутствует** в `server.vps.js`. |

Примечания:
- `addLog` не требует `adminPin` намеренно — отметки делает планшет, у которого нет (и не должно быть) PIN админки.
- `state`/`companies` не требуют авторизации вообще — см. [Безопасность](#безопасность), это сознательно принятый риск на текущем этапе.
- Действия, требующие `adminPin` (включая `checkAdminPin`), защищены от перебора — см. [Безопасность](#безопасность).
- CORS ограничен allowlist'ом доменов (не `*`) на всех трёх бэкендах — см. [Безопасность](#безопасность).
- `requestPinReset`/`resetPin`/`confirmEmail`/`resendConfirmation` — см. [Email и восстановление PIN](#email-и-восстановление-pin).
- **Все действия, кроме `register`/`companies`/`companyInfo`/`confirmEmail`/`resendConfirmation`, блокируются с `403 EMAIL_NOT_VERIFIED`**, пока email компании не подтверждён. Компании, созданные до этой фичи (без поля `emailVerified` в `companies.json`), считаются подтверждёнными автоматически — фича не блокирует уже работающих клиентов.

## Распознавание лица и liveness

Всё происходит в браузере планшета (`tablet.html`), сервер не участвует:

1. При регистрации сотрудника в админке (`admin.html`) камера снимает кадр, face-api.js считает 128-мерный дескриптор лица и сохраняет его вместе с фото в `employee.descriptor`/`employee.photo`.
2. На планшете каждые ~2.2 сек (`FULL_MATCH_INTERVAL_MS`) face-api.js детектирует лицо в кадре и считает евклидово расстояние (`faceapi.euclideanDistance`) между текущим дескриптором и дескрипторами всех сотрудников компании.
3. Совпадение засчитывается, если расстояние ≤ `settings.matchThreshold` (по умолчанию 0.55, настраивается 0.35–0.8 в админке).
4. Модель детекции выбирается в настройках: `tiny` (TinyFaceDetector, быстрее) или `ssd` (SSD MobileNetV1, точнее, тяжелее).
5. **Liveness-проверка** (анти-спуфинг): сотрудник должен моргнуть либо повернуть голову — это подтверждает, что перед камерой живой человек, а не фото на экране другого телефона. Реализовано через анализ EAR (eye-aspect-ratio) по `face_landmark_68` лендмаркам, с историей экспериментов и провалов в `data/git log` (опробованы и отброшены: пассивная проверка по фото, оптическая флеш-проверка, MiniFASNet-V2 — все не сработали на реальном железе или были обойдены).

**Текущий уровень защиты — одно подтверждённое моргание/поворот головы.** Известный риск: можно показать камере видео (а не статичное фото) с лицом коллеги и пройти проверку — buddy punching. Подробности и история попыток — в памяти `anti-spoofing-findings`.

## Фронтенды

### `index.html` — лендинг
- Только маркетинговая страница: заголовок, три карточки фич, ссылка на политику/оферту. Без форм и без списка компаний.
- Кнопка «Войти» (топбар) и CTA «Подключить компанию» / «У меня уже есть аккаунт» (геро-блок) ведут на `login.html`/`register.html`.

### `register.html` — регистрация компании
- Форма: название, slug (латиница/цифры/дефис, 3–32 символа, автогенерируется из названия пока не тронут вручную), PIN (≥4 символа), email, два обязательных чекбокса согласия → `action=register`.
- После успеха — экран «Проверьте почту» (без ссылок на админку/планшет, пока email не подтверждён) с кнопкой повторной отправки (`action=resendConfirmation`).
- Обрабатывает переход по ссылке из письма (`?confirm=1&c=slug&token=...`): вызывает `action=confirmEmail`, показывает результат, при успехе раскрывает ссылки на админку/планшет.
- Ссылка «Уже есть аккаунт? Войти» → `login.html`.

### `login.html` — вход
- Поле «Компания» принимает **slug или название** — резолвится клиентским запросом `action=companies` (точное совпадение без учёта регистра по `slug` или `name`).
- Поле PIN → `action=checkAdminPin` для резолвленного slug.
- При успехе: `sessionStorage.setItem('timetrack_admin_pin_' + slug, pin)` (тот же ключ, что использует `admin.html`) и редирект на `admin.html?c=slug` — повторного ввода PIN не происходит.
- При `403 EMAIL_NOT_VERIFIED` — переключается на отдельную панель с повторной отправкой письма подтверждения, не пытаясь молча залогинить.
- «Забыли PIN?» — отдельная панель (компания + email) → `action=requestPinReset`.
- Ссылка «Нет аккаунта? Создать» → `register.html`.

### `admin.html` — админка
- Вход по PIN (`checkAdminPin`), PIN кешируется в `sessionStorage` на время сессии браузера.
- **Дашборд** — кто сейчас на месте/опоздал, по сегодняшним логам.
- **Сотрудники** — CRUD, захват фото и дескриптора лица через камеру или загрузку файла.
- **Отчёты/табель** — фильтры по периоду/сотруднику, агрегация рабочих часов, экспорт в XLSX (через встроенный генератор) и CSV — и для табеля, и для сырых отметок.
- **Настройки** — смена PIN, порог распознавания, модель детекции, допуск опозданий (минуты), удаление компании (требует PIN + ручной ввод slug подтверждения).
- Кеширует state в `localStorage` (`STORE_KEY = timetrack_state_{slug}`) для быстрого повторного открытия.

### `tablet.html` — киоск
- Полноэкранный PWA-режим, ландшафтная ориентация, Wake Lock (не даёт экрану засыпать).
- Камера + распознавание + liveness (см. выше), кнопки «Пришёл» / «Ушёл» с защитой от повторной отметки (дубли отклоняются и на клиенте, и на сервере).
- Детект бездействия: после `SLEEP_AFTER_MS` (45 сек) уходит в режим ожидания, экономит ресурсы.
- Индикатор синхронизации (`Сервер` / `Локально · N в очереди`) — см. [Офлайн-режим](#офлайн-режим).
- Каждые 20 сек подтягивает свежий `state` с сервера (на случай если сотрудника добавили/удалили из админки).

## PWA / Service Worker

`sw.js` кеширует статические страницы (`index.html`, `admin.html`, `tablet.html`), манифест, иконки и **все веса моделей face-api.js**, чтобы планшет мог запуститься и узнавать лица даже при недоступном интернете. API (`/api.php`) и не-GET запросы из кеша исключены намеренно — кешировать данные нельзя, только статику и модели. При обновлении версии нужно поднять `CACHE_NAME` (`timetrack-pwa-v20` → `v21`...), иначе старые клиенты не увидят новых файлов.

## Офлайн-режим

Реализовано 2026-06-25. Раньше отметки, сделанные при недоступном интернете, не сохранялись (полная потеря данных учёта времени при сбое связи).

Текущая схема в `tablet.html`:
1. `Store.post('addLog', ...)` пытается отправить отметку на сервер.
2. Если сеть недоступна — отметка **(а)** сразу применяется локально (`state.logs.unshift`, мгновенный фидбек сотруднику) и **(б)** кладётся в персистентную очередь `localStorage['timetrack_queue_{slug}']` (`enqueueLog`).
3. Очередь дренируется (`flushQueue`) при: успешном `Store.load()`, успешном следующем `Store.post()`, и событии браузера `online`.
4. Отправка идёт по порядку (oldest-first), с защитой от дублей по `id`. Сервер отвечает `409`, если у него уже есть эквивалентная отметка (окно 120 сек) — такая запись тоже считается доставленной и удаляется из очереди. Любая другая ошибка сервера останавливает дренаж (без бесконечного спина на «ядовитой» записи) — попытка будет повторена при следующем триггере.
5. Индикатор синхронизации показывает количество отметок, ожидающих отправки: `Локально · N в очереди`.

## Email и восстановление PIN

Реализовано 2026-06-25. У проекта нет npm/Composer-зависимостей, поэтому почта отправляется собственным минимальным SMTP-клиентом по сырым сокетам (без PHPMailer/nodemailer): `stream_socket_client` в `api.php`, модуль `tls` в `server.js`/`server.vps.js`. Поддерживается только `AUTH LOGIN` через implicit TLS (порт 465) — это всё, что нужно текущему провайдеру.

**Настройка:**
- PHP: скопировать `smtp-config.example.php` → `smtp-config.php`, заполнить `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`. Если файла нет — отправка писем тихо отключается (в лог пишется предупреждение, остальной функционал работает как обычно).
- Node: скопировать `.env.example` → `.env` с теми же переменными. Самописный загрузчик `.env` без зависимостей (`loadEnvFile`), не переопределяет уже выставленные переменные окружения.
- **Оба файла (`smtp-config.php`, `.env`) в `.gitignore` — никогда не коммитятся.**

**Подтверждение email при регистрации.** Форма на `register.html` требует email. Компания создаётся сразу (директория, файлы, `adminPin`), но в `companies.json` помечается `emailVerified: false` — **в этом состоянии компания полностью неработоспособна**: `state`, `checkAdminPin` и все остальные действия отвечают `403 EMAIL_NOT_VERIFIED`, кроме `companyInfo`/`confirmEmail`/`resendConfirmation`.
1. После регистрации `register.html` показывает «Проверьте почту» (без ссылок на админку/планшет) и кнопку «Отправить письмо повторно».
2. Письмо содержит ссылку `register.html?confirm=1&c=slug&token=TOKEN` (токен на 24 часа, 128 бит, в `security.json`).
3. Переход по ссылке вызывает `action=confirmEmail` прямо со страницы регистрации; при успехе показывает «Email подтверждён!» и теперь раскрывает ссылки на админку/планшет.
4. Если пользователь вместо письма сразу пытается войти через `login.html` или открывает `admin.html?c=slug`, увидит отдельный блокирующий экран «Email компании ещё не подтверждён» с полем email и кнопкой повторной отправки (вместо обычного PIN-входа) — определяется по коду ошибки `EMAIL_NOT_VERIFIED` в ответе `action=checkAdminPin`/`action=state`.
5. **Совместимость:** компании, зарегистрированные до этой фичи (нет ключа `emailVerified` в их записи `companies.json`), считаются подтверждёнными автоматически («grandfather clause») — деплой не блокирует уже работающих клиентов. Заблокированным становится только то, что зарегистрировано заново после деплоя и не подтверждено.
6. tablet.html не показывает отдельного экрана про неподтверждённый email — он просто не получит данных сотрудников через `state` (упадёт в пустой локальный кэш), так как до подтверждения у компании физически нет смысла настраивать киоск.

**Восстановление PIN.** На `login.html` («Забыли PIN?») и на экране входа в `admin.html`:
1. Админ вводит компанию (slug/название) + email → `action=requestPinReset` (с резолвленным slug). Если email совпадает с email компании, генерируется случайный токен (128 бит) на 30 минут и отправляется письмом со ссылкой `admin.html?c=slug&reset=TOKEN`. Ответ всегда одинаковый («если email верный — проверьте почту»), чтобы не показывать, привязан ли конкретный email к компании. Не больше одного письма на компанию каждые 2 минуты.
2. Переход по ссылке открывает `admin.html` сразу в режиме «задать новый PIN» (без обычного экрана входа).
3. Новый PIN → `action=resetPin` с токеном. Сервер сравнивает токен константным по времени способом (`hash_equals`/`crypto.timingSafeEqual`), проверяет срок действия, обновляет `adminPin`, инвалидирует токен.
4. Успешный обычный вход по старому PIN тоже инвалидирует любой висящий токен сброса.

⚠️ **Известное ограничение на момент написания:** SMTP-хост `smtp.timetrack.kz`, указанный для этого проекта, **не резолвится в DNS** (нет A/CNAME-записи, только SRV `_smtps._tcp`, указывающая на несуществующий хост). MX-запись домена ведёт на `mail.timetrack.kz` (резолвится на VPS `194.238.42.177`), но порты 25/465/587 там закрыты (`ECONNREFUSED`) — почтовый сервер не поднят либо не открыт в файрволе. Код готов и протестирован на уровне протокола/синтаксиса, но не может быть проверен end-to-end и не будет реально отправлять письма, пока почтовая инфраструктура на сервере не настроена.

## Безопасность

Авторизация — единый PIN на компанию (`settings.adminPin`), хранится **в открытом виде** в `settings.json`, передаётся в каждом запросе. Это остаётся так (нет учётных записей по сотрудникам/ролям, нет аудита кто что сделал) — но с 2026-06-25 подбор PIN ограничен (см. ниже).

**Сознательно принятые риски (закреплены решением 2026-06-25, не изменились):**
- `action=state` отдаёт фото и биометрические дескрипторы сотрудников **без проверки PIN** — это нужно планшету для распознавания лиц, у которого нет своих учётных данных.
- `action=companies` публично перечисляет все зарегистрированные компании — используется лендингом для каталога.
- Совокупный эффект: зная (или подобрав) slug компании, можно прочитать список сотрудников вместе с их фото и дескрипторами лиц без какой-либо авторизации.

**Что исправлено 2026-06-25:**
- **Защита от перебора PIN.** `require_admin_pin()`/`requireAdminPin()` (api.php, server.js, server.vps.js) считает неверные попытки в `data/{slug}/security.json`. После 6 ошибок подряд — блокировка компании на 15 минут (`MAX_PIN_ATTEMPTS`/`PIN_LOCKOUT_SECONDS`); во время блокировки даже верный PIN отклоняется (`429`), что убирает тайминг-атаку (нельзя понять, был ли введённый PIN правильным).
- **CORS сужен.** Вместо `Access-Control-Allow-Origin: *` — allowlist (`$ALLOWED_ORIGINS`/`ALLOWED_ORIGINS`): `https://timetrack.kz`, `https://www.timetrack.kz`, `http://localhost:8787`, `http://127.0.0.1:8787`. Заголовок выставляется только если `Origin` запроса есть в списке. При смене домена или добавлении staging-окружения — обновить список во всех трёх бэкендах.
- **Согласие на оферту/политику конфиденциальности.** Регистрация компании (`register.html`) требует два обязательных чекбокса (HTML `required` + JS-проверка перед отправкой); бэкенд тоже отклоняет `register` без `acceptedPolicy`/`acceptedOffer` (`422`). Факт согласия с timestamp сохраняется в `companies.json` (`consent.acceptedAt`) как доказательство для аудита. Тексты — [privacy.html](privacy.html) и [offer.html](offer.html), **черновики**, явно помечены как требующие юридической проверки перед коммерческим использованием.
- **Локальные бэкапы.** См. [Модель данных](#модель-данных) — снапшоты `employees.json` после каждого сохранения сотрудника, не защищают от потери всего диска/сервера (нет offsite-копии).

Подробный список того, чего ещё не хватает для безопасного запуска в production (биллинг, email-верификация, масштабирование), а также история решений — см. `production-readiness.md` в auto-memory проекта.

Что было сделано раньше:
- `adminPin` исключается из всех публичных ответов (`public_state`/`publicState`).
- Каталог компании под `.htaccess` `Require all denied` (PHP-прод) — покрывает и новые `employees.json`/`settings.json`/`logs.json`/`security.json`/`backups/`.
- Удаление компании требует PIN **и** ручного ввода slug для подтверждения.
- Серверный лок на запись (`flock`/файловый лок) — конкурентные запросы к одной компании не бьют друг друга по данным.

## Локальная разработка

```bash
node "timetrack poscenter/server.js"
# открыть http://localhost:8787/
# планшет:  http://localhost:8787/tablet.html?c=poscenter
# админка:  http://localhost:8787/admin.html?c=poscenter
```

`server.js` отдаёт и статику, и API на одном порту (`PORT`, по умолчанию `8787`). Тестовые компании (`poscenter`, `other-co`) уже есть в `data/`.

## Деплой

Продакшн (см. память `server-structure`):
- **Веб-сервер:** Caddy.
- **Статика:** отдаётся файл-сервером напрямую.
- **API (`/api.php*`):** обрабатывается напрямую PHP (если хостинг с PHP) **или** проксируется на Node.js-контейнер с `server.vps.js`.
- Деплой — вручную (rsync на сервер), без CI/CD. Подробный процесс и серверные особенности — в памяти `server-structure`/`deployment-state`.

## Известные ограничения

- **`server.vps.js` отстаёт от `api.php`/`server.js`**: на момент написания не реализует `deleteCompany`. Логика одного и того же API дублируется вручную в трёх местах (`api.php`, `server.js`, `server.vps.js`) — при любом изменении контракта нужно править все три или явно выбрать один источник правды.
- **Нет базы данных** — JSON-файлы на диске (с 2026-06-25 разнесены на `employees.json`/`settings.json`/`logs.json` на компанию, что устранило главный горячий путь — `addLog` больше не перезаписывает фото и дескрипторы сотрудников при каждой отметке). Это снимает основную проблему производительности на раннем этапе, но это всё ещё файловое хранилище: не масштабируется на десятки активных компаний одновременно так, как реальная БД (нет индексов, нет транзакций между файлами, поиск/фильтрация — это full-scan в памяти).
- **Нет биллинга** — регистрация мгновенная и бесплатная (отложено осознанно).
- **Email/восстановление PIN реализованы в коде, но не работают на проде** — SMTP-хост `smtp.timetrack.kz` не резолвится в DNS, а почтовый сервер на `mail.timetrack.kz` (хост из MX-записи) не принимает соединения на 25/465/587. См. [Email и восстановление PIN](#email-и-восстановление-pin).
- **Бэкапы — только локальные**, на том же диске, что и сами данные. Не защищают от потери сервера/диска целиком.
- **`timetrack-legacy.html`** оставлен в репозитории для истории, в проде не используется и не поддерживается.
